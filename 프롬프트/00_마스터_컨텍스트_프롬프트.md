# KORAIL LINK 빌드 프롬프트 세트 — Part 0. 마스터 컨텍스트

> 이 파일은 새 코딩 에이전트 세션(예: Claude Code)을 열고 **가장 먼저** 붙여넣는 프롬프트다. 이후 `01_Phase0_...` 부터 `07_Phase7_...`까지 파일을 하나씩, 순서대로, 별도 턴으로 붙여넣는다. 한 Phase가 끝나고 그 프롬프트가 요구하는 "완료 조건(DoD)"을 통과했는지 확인한 뒤에만 다음 Phase로 넘어간다 — 확인 없이 이어붙이면 뒤 Phase가 앞 Phase의 미완성 위에 쌓여 망가진다.

---

## 0. 너는 무엇을 만드는가

너는 **KORAIL LINK**를 처음부터 새로 만드는 코딩 에이전트다. KORAIL LINK는 코레일의 국제복합운송(유라시아 철도, 한국→중앙아시아) 업무를 지원하는 해커톤 데모 플랫폼이다. 핵심은 두 가지다.

1. **운임 인텔리전스** — 과거 유사 운송 데이터와 현재 시황(환율·유가·해상운임지수·뉴스)을 비교해 견적의 적정성을 AI가 검증한다.
2. **Single Data Entry + 업무 연결** — 화물 정보를 한 번만 입력하면, 견적 → 계약 → 문서 → 정산까지 같은 기준 데이터(Case Master Data + Cost Ledger)를 계속 재사용한다.

이 프로젝트는 대회 과제 TASK 03(국제물류 지원 확장)과 TASK 06(계약-운임-정산 AX)이 겹치는 지점을 하나의 플랫폼으로 통합한 것이다.

## 1. 참고 문서 3종 — 반드시 먼저 읽는다

프로젝트 루트의 `docs/` 폴더(또는 네가 배치한 경로)에 아래 3개 파일이 있다. **각 Phase 프롬프트는 이 문서의 특정 섹션(A-1, B-5, 백엔드 문서 5번 등)을 그대로 참조한다** — 이 프롬프트 세트는 문서 내용을 요약·재복사하지 않으므로, Phase 프롬프트를 실행하기 전에 지시된 섹션을 실제로 열어서 읽어야 한다.

- `docs/KORAIL_LINK_서비스_개요.md` — 이 서비스가 왜 필요하고 무엇이 다른지, 경쟁 서비스 비교, 서비스 이용 흐름(IA 포함).
- `docs/KORAIL_LINK_기능_상세_스펙.md` — **가장 자주 열어볼 문서.** 기능 A(A-1~A-9)·기능 B(B-0~B-9)의 정확한 판정 공식·데이터 처리 로직. 하단 부록 A~E에 이전 프로토타입의 구현 가이드·구현 현황·기술스택·알려진 한계·설계 결정 히스토리가 들어 있다.
- `docs/KORAIL_LINK_백엔드_연동.md` — 외부 API·LLM·전자서명·DB·인증 등 11개 항목의 연동 현황과 필요 작업. Phase 6(백엔드 실연동)에서 주로 쓰지만, Phase 0의 DB 스키마는 이 문서의 9번 항목을 기준으로 한다.

이 세 문서는 프로젝트가 끝날 때까지 **살아있는 참조 문서**로 취급한다 — 구현하면서 스펙과 다르게 판단해야 하는 지점이 생기면(예: 허용오차 값 조정, 새 필드 추가) 코드만 바꾸지 말고 해당 문서도 같이 갱신한다.

## 2. 비타협 설계 원칙 (모든 Phase에 공통 적용)

아래 원칙은 기능 상세 스펙 문서 전체에 반복해서 나오는 설계 철학이다. 개별 Phase 프롬프트에 다시 안 적혀 있어도 항상 지킨다.

1. **같은 정보를 다음 단계에서 다시 만들지 않는다.** 견적에서 확정한 구간별 비용(Cost Ledger)은 계약·정산이 그대로 재사용한다. 총액을 나중에 다시 임의 비중으로 쪼개는 방식(`splitCostByStages` 류)은 Cost Ledger가 없는 레거시 데이터의 화면 표시용 fallback으로만 허용한다.
2. **AI는 최종 결정을 대신하지 않는다.** 정보 추출 → 기존 정보와 대조 → 판단 근거 설명 → 문서 초안 생성, 이 네 가지가 AI의 역할이다. 최종 반영·확정은 항상 담당자 승인을 거친다.
3. **문서에서 추출한 값이 기존 Case 기준값과 다르면 자동으로 덮어쓰지 않는다.** `현재 값 유지 / 문서 값 반영 / 확인 필요` 중 담당자가 선택해야 Case Master Data가 갱신된다. 반영 시 문서유형·파일명·변경전값·변경후값·처리시점을 이력으로 남긴다.
4. **판정 문구는 서술형이지 지시형이 아니다.** "재협상이 필요합니다"가 아니라 "과거에 비해 높은 견적입니다"처럼 서술하고, 왜 그런지는 별도 근거 카드로 분리한다.
5. **근거 없는 내용을 규정·국제기준처럼 표현하지 않는다.** 실제 지식베이스(SMGS 등)에 출처가 있는 항목만 "협약/계약조건" 근거로 표시하고, 없으면 `AI 리스크 권고` 또는 `내부 운영 검토 필요`로 명확히 구분한다.
6. **추출 실패는 `불일치`가 아니라 `확인 필요`다.** 빈 값·임의값을 채우지 않는다.
7. **목업은 목업이라고 화면에 라벨링한다.** 특히 "KORAIL LINK 종합 지수"·"자체 산출 지수(KCCI/KCI 벤치마킹 참고)"·유사도 가중치("MVP 초기 휴리스틱") 등은 외부 공식 지수처럼 오해되지 않도록 라벨을 명시적으로 붙인다.
8. **결정론적 시뮬레이션을 우선한다.** LLM 실시간 호출을 Phase 6 전까지는 붙이지 않는다 — 문서 추출·이의제기 챗봇·시황 인과분석은 모두 Case/시장 데이터를 입력받아 항상 같은 규칙으로 같은 결과를 내는 함수로 구현한다(그래야 데모 중 결과가 들쭉날쭉하지 않는다).

## 3. 기술 스택 (기본값)

이전 프로토타입에서 이미 검증된 조합을 그대로 재사용한다. 근거는 `기능_상세_스펙.md` 부록 C 참고.

- **[vinext](https://github.com/cloudflare/vinext)** — Cloudflare Workers 위에서 도는 Next.js App Router 스타터(Vite 기반)
- React 19, TypeScript, Tailwind CSS
- **Supabase** — Auth(이메일 로그인/회원가입), Postgres(스키마는 Phase 0에서 확정), Storage(문서 업로드)
- Cloudflare D1/Drizzle은 **쓰지 않는다** — 이전에 후보로 검토했지만 실제로는 Supabase로 대체됐다(백엔드 연동 문서 9번 참고).

> 이 스택을 그대로 쓰기 어렵다면(예: Cloudflare 계정이 없다) Next.js(Vercel) + Supabase 조합으로 바꿔도 이 프롬프트 세트의 나머지 내용은 대부분 그대로 유효하다. 스택을 바꿀 경우 Phase 0을 시작하기 전에 사용자에게 확인받는다.

## 4. 지난 프로토타입에서 배운 것 — 이번엔 반복하지 않을 실수

`기능_상세_스펙.md` 부록 E(설계 결정 히스토리)에 기록된 시행착오 중, 처음부터 새로 지을 때 미리 피할 수 있는 것들이다.

- **Supabase를 UI보다 나중에 붙이지 말 것.** 지난번엔 `setCases`를 Supabase 저장 래퍼로 바꾸면서 타입을 배열로만 좁혔는데, 실제 호출부는 업데이터 함수(`setCases(xs => xs.map(...))`) 형태였어서 런타임 에러가 날 뻔했다. 이번엔 Phase 0에서 처음부터 `CaseItem[] | ((prev: CaseItem[]) => CaseItem[])`를 받는 상태 관리 래퍼를 설계하고, 이후 모든 Phase가 이 래퍼 위에서 작업한다.
- **로컬 상태 우선 + best-effort DB 동기화 패턴을 유지할 것.** Supabase 저장이 실패해도(RLS, 네트워크 등) 화면 상태는 항상 로컬 갱신을 우선하고, 저장 실패는 토스트로만 알린다. 모든 Supabase 호출은 `.catch()`로 감싼다 — 데모 중 DB 장애로 화면이 깨지면 안 된다.
- **σ(가격 분산)와 diffPct(기준값 대비 수준편차)는 같은 성격의 통계량으로 정의할 것.** 처음부터 "가격 수준편차" 정의로 σ를 만들고, 판정은 절대값 기준 대칭으로(지나치게 낮은 견적도 "확인 필요"로 잡히게) 설계한다. `기능_상세_스펙.md` A-1 참고.
- **세금계산서 세율은 고정 10%가 아니라 국제운송용역 기준 영세율(0원)을 기본값으로.** B-7 참고.
- **포워더를 여러 곳 비교하는 구조로 설계하지 말 것.** 코레일 단일 주체 전제로, "포워더(견적 산정 담당)"와 "검증 담당자"를 같은 코레일 내부의 다른 역할로 설계한다.
- **사이드바 IA는 "운임 인텔리전스 vs 업무 연결"(기능 축)이 아니라 "리서치 vs 파이프라인"(작업 단계 축)으로.** 계약·문서·정산은 독립 기능이 아니라 화물 운송(Case) 하나에 속한 하위 뷰라서, 처음부터 "화물 운송" 아코디언 하위에 넣는다. `서비스_개요.md` 4장 참고.

## 5. Phase 개요

| Phase | 무엇을 만드는가 | 주로 참고할 스펙 섹션 |
|---|---|---|
| 0 | 프로젝트 셋업, Case Master Data + Cost Ledger 데이터 모델, Supabase 스키마 전체, 인증 | B-0, 백엔드 연동 9·11번, 부록 C |
| 1 | IA 셸(리서치/파이프라인 사이드바), 대시보드, 시황 지표, 뉴스·인과분석, 정보검색 | A-2, A-4~A-8, A-5, 서비스개요 4장 |
| 2 | 견적 생성(구간별 원가 합산) + AI 견적 적정성 검증 + Cost Ledger 저장 | A-1, A-3, A-9 |
| 3 | 계약 — 근거 기반 특약 추천 → 검토 → 계약서 초안 → 전자서명 시뮬레이션 | B-2, B-6 |
| 4 | 문서 — 업로드·AI 추출 시뮬레이션·Case Master Data 대조·승인 반영, 화물운송장 | B-1, B-2, B-3, B-4 |
| 5 | 정산 — Cost Ledger↔Invoice 라인별 대조, 세금계산서, 이의제기 챗봇 | B-5, B-7, B-8 |
| 6 | (선택) 백엔드 실연동 — 외부 API·LLM 문서추출·챗봇·전자서명 SDK | 백엔드 연동 1~7번 |
| 7 | 통합 QA·데모 준비 | 부록 A-7 통합테스트 시나리오 |

Phase 0~5는 필수다. 시간이 부족하면 Phase 6(백엔드 실연동)은 항목별로 골라서 하거나 통째로 건너뛰어도 된다 — 그 경우 Phase 7에서 "이건 목업입니다"를 화면에 명확히 라벨링하는 것으로 대체한다. 우선순위는 Phase 6 프롬프트에 별도로 정리되어 있다.

## 6. 각 Phase가 끝날 때마다 할 일

Phase 프롬프트 각각에는 "완료 조건(DoD)" 체크리스트가 있다. 코드를 다 짠 뒤:

1. DoD 항목을 하나씩 실제로 확인한다(화면을 켜보거나 `npx tsc --noEmit`을 돌리는 등 — 체크리스트에 방법이 적혀 있다).
2. 통과하지 못한 항목이 있으면 다음 Phase로 넘어가지 말고 고친다.
3. 그 Phase에서 스펙 문서와 다르게 구현하기로 판단한 부분이 있다면(있을 수 있다 — 스펙에도 "MVP 초기 휴리스틱" 같은 표현이 곳곳에 있다) 무엇을, 왜 다르게 했는지 한 문단으로 요약해서 보고한다.
4. 다음 Phase 프롬프트를 요청한다.
