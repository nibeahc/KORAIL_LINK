# KORAIL LINK 빌드 프롬프트 세트 — Phase 2. 견적 생성 · 검증

> 전제: Phase 1 DoD를 통과했다. 지금 열어서 같이 읽을 문서: `기능_상세_스펙.md`의 A-1(견적 적정성 판정), A-3(유사 견적 매칭), A-9(견적서 자동생성 + Cost Ledger 저장).

## 목표

파이프라인 사이드바의 "견적 생성"부터 Case 상세의 "견적 검증" 탭까지 — 화물 정보 최초 등록, 구간별 원가 문서 업로드(파일 내용은 안 읽는다, B-9 참고) → 견적 초안 생성 → σ 기반 적정성 검증 → 확정 시 Cost Ledger 저장까지 전체 플로우를 만든다. **이 Phase가 이 서비스의 핵심이다 — 시간이 부족하면 다른 Phase보다 이 Phase에 시간을 더 쓴다.**

## 6-1. 과거 유사 견적 풀 — historicalQuotes

A-3 마지막의 cold start 설명대로, 코레일 실거래 이력이 없으므로 목업 데이터로 채운다.

- 최소 30건 이상(이전 프로토타입 기준 33~44건). 노선·컨테이너 타입·화물 특성·계약일·금액을 다양하게 조합해서, Phase 2의 유사도 매칭·σ 판정 로직이 실제로 갈라지는 결과를 낼 수 있게 한다(전부 비슷한 값이면 검증 로직이 항상 "적정"만 나와서 데모 가치가 없다).
- Phase 0에서 `historical_quotes` 테이블을 만들었다면 이 데이터를 그 테이블에 시드(seed)한다. 아니면 `marketData.ts`처럼 하드코딩 배열로 둬도 된다 — 어느 쪽이든 이후 로직은 `HistoricalQuote[]` 타입만 보고 동작하게 짠다.

## 6-2. 유사 견적 매칭 — A-3

가중치 기반 유사도:

- 노선(출발–도착) 일치: 40%
- 컨테이너 타입/규격 일치: 25%
- 운송 시기 유사도(±N개월): 20%
- 화물 특성 유사도: 15%
- 유사도 70% 이상 & 최근 6개월 이내만 채택. 표본 4건 미만이면 A-1의 기본 σ 규칙으로 넘어간다.

**화면에 이 가중치·70%·6개월 값을 그대로 노출**하고 "MVP 초기 휴리스틱, 실 서비스 전환 시 재검증 필요"라는 문구를 견적 검증 탭의 "비교 조건" 카드에 넣는다(A-3 마지막 항목 — 스펙이 이 노출을 명시적으로 요구한다).

## 6-3. 견적 적정성 판정 — A-1 (동적 σ, 대칭 판정)

정확한 공식이므로 그대로 옮긴다 — 절대 임의로 단순화하지 않는다.

```
baseline = 유사 견적 그룹의 중앙값
σ = 유사 견적들의 "가격 수준"이 baseline 대비 흩어진 정도의 표준편차(%)
    표본 4건 미만이거나 baseline=0 → σ 기본값 5%
    산출값 1.5% 미만 → σ 하한 1.5%
diffPct = (현재 견적 − baseline) / baseline × 100

판정은 |diffPct| 기준 대칭:
  |diffPct| ≤ 0.5σ           → 적정 수준
  0.5σ < |diffPct| ≤ 1.5σ    → 다소 높음(diffPct>0) / 다소 낮음·비용 확인 필요(diffPct<0)
  |diffPct| > 1.5σ            → 높음(diffPct>0) / 낮음·비용 누락 가능성(diffPct<0)
```

**diffPct가 음수라고 무조건 "유리한 견적"으로 판정하지 않는다** — 이게 이전 프로토타입에서 팀원 피드백으로 고친 핵심 버그다(Part 0의 "지난 프로토타입에서 배운 것" 참고). 지나치게 낮은 견적도 원가 누락 가능성으로 "확인 필요"가 뜨게 만든다.

판정 문구는 서술형("과거에 비해 높은 견적입니다")으로, 왜 높은지는 A-4의 인과분석 카드(Phase 1에서 만든 `causalAnalysis.ts`)를 그대로 재사용해 별도 카드로 붙인다. **별도 "포워더 확인" 체크리스트 탭은 만들지 않는다** — 검증 결과 확인 후 바로 견적 확정 버튼으로 이어진다.

## 6-4. 견적서 자동생성 — A-9 (구간별 합산, Cost Ledger 저장)

- Case Master Data에 화물 기본정보(화주·품목·출발지/도착지·중량/수량·일정·운송조건)를 입력해 초기값을 만드는 화면부터 시작한다(B-1 참고, Case 등록 화면).
- 구간별 원가 문서를 업로드하면(파일 내용은 읽지 않는다) `buildQuoteDraft()`가 **routeData의 구간 구성(Phase 1에서 만든 것)마다** 결정론적으로 금액을 추출한 것처럼 산출해 `lines`(구간별 금액)와 `total`을 함께 만든다. 과거 유사 견적 중앙값은 총액을 만드는 재료가 아니라, 6-3의 σ 판정으로 **검증에만** 쓴다(A-9의 "인과관계 재정렬" — 순서를 거꾸로 하지 않는다: 구간별 금액을 먼저 만들고 합산 → 검증은 별도).
- **견적 확정 시 총액뿐 아니라 구간별 금액도 Cost Ledger로 저장한다.** 여기서 만든 `CostLedgerLine[]`이 Phase 3(계약 별첨)·Phase 5(정산 대조)의 유일한 기준 데이터가 된다 — 나중에 총액을 임의 비중으로 재분배하는 계산은 이 시점 이후 두 번 다시 하지 않는다(비타협 원칙 1).

## 완료 조건 (DoD)

- [ ] 새 Case를 만들고 화물 기본정보를 입력하면 Case Master Data 초기값이 생긴다.
- [ ] 구간별 원가 문서를 업로드(파일 형식 무관, 내용은 안 읽어도 됨)하면 구간별 금액 + 합계가 결정론적으로 나온다 — 같은 Case에 다른 파일을 올려도 결과가 같은지 확인(B-9 명시 한계와 일치해야 함).
- [ ] 유사 견적 매칭 결과와 σ 판정이 "비교 조건" 카드에 가중치·임계값과 함께 노출된다.
- [ ] diffPct가 음수인 케이스(일부러 낮은 견적으로 테스트)에서도 "확인 필요" 판정이 뜨는지 확인 — 무조건 "유리함"으로 뜨면 A-1을 잘못 구현한 것이다.
- [ ] 견적을 확정하면 `CaseItem.costLedger`에 구간별 라인이 저장되고, `price`(총액)와 `costLedger` 합계가 일치한다.
- [ ] Case 상태가 "견적 확정"으로 바뀌고 `case_status_history`에 기록된다(Phase 0에서 만든 테이블).
