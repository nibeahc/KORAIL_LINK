# KORAIL LINK 빌드 프롬프트 세트 — Phase 4. 문서

> 전제: Phase 3 DoD를 통과했다. 지금 열어서 같이 읽을 문서: `기능_상세_스펙.md`의 B-1(최초 1회 입력 + 문서 보완), B-2(Case별 업로드 문서 — 두 번째 종류), B-3(AI 수행 흐름), B-4(대조 로직).

## 목표

계약서·Packing List·화물운송장(SMGS)·B/L을 업로드하면 AI가 필드를 추출한 "척"하고(B-9 — 실제 파일 내용은 읽지 않는다), Case Master Data와 대조해서, **담당자가 승인해야만** Case 값이 바뀌는 흐름을 만든다. 화물운송장은 업로드뿐 아니라 AI가 초안을 직접 써주는 기능도 만든다.

## 8-1. 문서 업로드 — 대상과 제약

- 1차 파싱 대상(이번에 만든다): **계약서, Packing List, 화물운송장(SMGS), B/L(해상 구간)**. Invoice는 Phase 5(정산)에서 별도로 다룬다.
- 업로드 시 사용자가 문서 유형을 **직접 선택**한다 — 자동분류는 하지 않는다(오분류로 인한 잘못된 대조를 막기 위한 의도적 단순화, B-2).
- 파일 형식은 PDF/이미지(JPG/PNG)를 UI상 허용하되, 실제로 파일을 읽어서 파싱하지는 않는다 — Case 데이터를 바탕으로 "AI가 추출했다면 이랬을 것"이라는 **결정론적** 결과를 생성한다(같은 Case면 어떤 파일을 올려도 결과가 같아야 한다, B-9).
- Container List·통관서류·환적확인서 등 2차 확장 대상은 이번엔 만들지 않는다 — B-2에 정의된 1차 파이프라인과 같은 구조로 나중에 확장 가능하게만 코드를 짜둔다(문서유형 enum에 추가하기 쉬운 형태로).

## 8-2. 문서별 AI 추출 시뮬레이션 — B-3

공통 흐름: **문서 업로드/생성 → AI 필드 추출(시뮬레이션) → Case Master Data와 대조 → 담당자 확인 → 승인된 값만 Case에 반영.**

- **계약서**: 확정 금액·운송조건·특약사항 추출. KORAIL LINK가 만든 계약 초안을 그대로 확정한 경우엔 그 값을 계약 기준정보로 저장하고, 외부 계약서를 다시 올리면 저장된 값과 대조한다.
- **Packing List**: 화주명·품목·출발지/도착지·컨테이너 타입·수량·총중량 추출 → Case Master Data와 대조.
- **화물운송장(SMGS)**: 두 경로 모두 만든다.
  1. **AI 초안 생성**: Case Master Data의 화주·수취인·노선·품목·중량·컨테이너를 자동으로 채우고, Phase 3에서 만든 SMGS 참조 데이터로 필수정보·첨부서류를 체크한다. 값이 없는 필드는 `추가 입력 필요`로 남긴다(임의 생성 금지). 문서 미리보기 → PDF 출력 흐름을 만든다.
  2. **기존 문서 업로드**: 필드 추출 + Case Master Data 대조 + SMGS 체크리스트를 함께 수행한다.
- **B/L(해상 구간)**: 화주·컨테이너는 Case 전체 기준과 대조하지만, 출발지/도착지는 routePath(Phase 1)의 **해상 구간만** 대조한다(부산항→연운항 등).
- 추출 실패 필드는 빈 값·임의값이 아니라 `확인 필요`로 남긴다.

## 8-3. 대조 로직 — B-4

- 비교 대상: Case Master Data 현재 기준값 vs 새 문서 추출값.
- **식별자·화폐 필드(화주명·출발지/도착지·컨테이너 타입·확정 금액)는 정규화 후 완전일치**로 판정한다(허용오차 없음). 정규화 규칙에는 최소한 법인 접미사, 단위, 컨테이너 규격(FT/피트/하이큐브), 지명 별칭을 반영한다.
- **총중량처럼 계측 지점 차이가 있을 수 있는 필드에만 제한적 허용오차**를 둔다 — 데모 기준 ±0.3톤(화면에 "데모용 설계값, 실제 업무 기준 확정 아님"이라고 표시한다).
- 추출 실패는 `불일치`가 아니라 `확인 필요`.
- 결과 배지: `일치 / 확인 필요 / 불일치`.
- **불일치가 발견돼도 AI가 자동으로 Case Master Data를 고치지 않는다.** 담당자는 `현재 값 유지 / 문서 값으로 반영 / 확인 필요로 보류` 중 하나를 고른다.
- `문서 값으로 반영`을 선택하면 **문서 유형·파일명·변경 전 값·변경 후 값·처리 시점**을 Phase 0에서 설계한 `changeHistory`에 남긴다.

## 8-4. 문서 정합성 화면 — B-3 하단

각 문서를 개별로 보는 화면과 별개로, **동일한 Case Master Data 필드를 기준으로 문서별 추출값을 한 화면에 모아 보여준다.**

```
총중량 | Case 58.0t | Packing List 58.0t | 화물운송장 59.2t → 확인 필요
```

문서↔문서를 직접 비교하는 로직을 따로 만들지 않는다 — 모든 문서를 같은 Case Master Data에 대조하기만 하면, 이 화면에서 문서 간 불일치도 자연히 드러난다(B-3 핵심 설계 포인트).

## 완료 조건 (DoD)

- [ ] 계약서/Packing List/화물운송장/B/L 4종 업로드가 모두 되고, 업로드 시 문서 유형을 사용자가 직접 고른다.
- [ ] 같은 Case에 파일명만 다른 두 파일을 올려도 추출 결과가 동일하다(결정론성 확인).
- [ ] Case 기준값과 다른 값을 추출하도록 일부러 유도했을 때(테스트용 Case 값 조작), Case Master Data가 자동으로 바뀌지 않고 `현재 값 유지/문서 값 반영/확인 필요` 선택지가 뜬다.
- [ ] `문서 값으로 반영`을 선택하면 Case 값이 바뀌고, 변경이력에 문서유형·파일명·전/후 값·시점이 남는다.
- [ ] 총중량 허용오차(±0.3톤)와 화주명 등 완전일치 필드가 서로 다른 판정 기준으로 동작한다(총중량은 근소한 차이를 "일치"로, 화주명은 근소한 표기 차이도 정규화 후 비교).
- [ ] 화물운송장을 "AI로 초안 생성"하면 Case Master Data 기반으로 필드가 자동으로 채워지고, 없는 필드는 `추가 입력 필요`로 표시된다.
- [ ] 문서 정합성 화면에서 여러 문서의 같은 필드(예: 총중량)를 한 표로 볼 수 있다.
